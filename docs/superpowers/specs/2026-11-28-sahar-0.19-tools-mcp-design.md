# Sahar 0.19 — tools and MCP

*2026-11-28. Phase 2 of the owner-approved Jarvis roadmap (`/home/claude/sahar-design/specs/2026-11-27-jarvis-roadmap.md`).
Research behind every choice: `/home/claude/sahar-design/research/2026-11-28-phase2-tools-mcp.md` (course lessons, MCP
spec, llama.cpp, free APIs, similar projects). Design approved by the owner in chat on 2026-11-28; rulings taken while
building go to the ledger and are copied to §11.*

## 1. Goal and the felt success criterion

Sahar can **use tools he gives her**: any MCP server he adds himself, plus two built-in media tools (make a picture,
make a voice clip). Every tool is visible, approved by him, isolated, and cannot talk her into anything.

Felt criterion: *"I add a tool in one page, ask her in the chat window, she asks me once (or not, if I said always), the
result shows up right there, and nothing on my laptop happens that I did not see."*

Not in 0.19: video (no verified free API: the button stays hidden), Node/Python MCP servers, OAuth MCP servers, her own
speaking voice (phase 6, local, built into her), the big local model (0.18).

## 2. Owner decisions (2026-11-28, verbatim intent)

| # | Decision |
|---|---|
| D1 | Order: the general MCP connection first, then pictures, then voice clips. |
| D2 | Her own voice stays as decided before: her own, built in, offline, last (phase 6). 0.19's "voice" is a *tool* that makes a clip on request. |
| D3 | MCP servers that need Node/Python are not supported in 0.19. Later, only after she asks him, and only the official runtime. |
| D4 | "Always allow" is available for every tool, **except** tools that delete, send something in his name, or touch money: those ask every time. |
| D5 | Video button hidden until a provider is chosen. |

## 3. Facts the design rests on (checked 2026-11-28)

- MCP spec **2026-07-28**: no `initialize` handshake, no sessions; `_meta` on every request; servers MUST implement
  `server/discover`. Transports: stdio, and POST-only Streamable HTTP (`MCP-Protocol-Version`, `Mcp-Method`, `Mcp-Name`).
- Official C# SDK NuGet `ModelContextProtocol.Core` **2.4.0**: implements 2026-07-28, falls back to the 2025-11-25
  handshake by itself, all projects `IsAotCompatible`. Sahar uses the client side only (`McpClient`,
  `StdioClientTransport`, `HttpClientTransport`). Zero trim warnings in *our* AOT build is checked in Task 1, not assumed.
- llama.cpp b12207 supports OpenAI `tools` and Gemma 4's native tool format, but an independent test found Gemma 4 E4B
  weak at real tool use (2/6 scenarios). So tool choice keeps going through her **existing grammar-constrained decision
  JSON**, which already works.
- Pollinations image endpoint: no key, one image at a time per IP, at least 45 s apart; over the limit it answers 402
  with `Retry-After`.
- Groq `canopylabs/orpheus-arabic-saudi`: Saudi dialect, preview, under 200 characters per request, free limit shown as
  10 req/min and 100 req/day; works with the Groq key he already sealed in 0.17.

## 4. Architecture

```
chat window / bubble ─► Sahar.Mind TurnRunner (local decision JSON, unchanged loop)
                              │  decision {tool:"mcp.<server>.<tool>" | "image.make" | "voice.make", args}
                              ▼
                      Engine: ToolRegistry.Validate ─► AutonomyPolicy.Decide (+ ToolGrants) ─► ask card / act
                              │
               ┌──────────────┴───────────────┐
        built-in media (Mind, HTTP)     McpHost (inside Sahar.Mind)
        image.make → Pollinations        one McpClient per enabled server
        voice.make → Groq Orpheus        stdio .exe → own Windows Job Object
                                         HTTP → https or 127.0.0.1 only
                              │
                      ToolOutput.Sanitize ─► result card in chat (verbatim, marked "from <tool>")
                              ▼
                      optional second, tool-less step: she reads the sanitized output and answers in words
```

- **The MCP client lives in Sahar.Mind**, not in the Engine and not in a new process. Mind is already a separate
  process with the network and the sealed keys; each stdio server is its own child process in its own Job Object
  (kill-on-close, 512 MB memory cap), so a broken server cannot freeze her body or the brain.
- The Engine's `ITool.Run` stays synchronous on the UI thread. MCP and media tools are **Mind-side tools**: the Engine
  only validates, decides (ask/act/refuse) and shows; the call itself runs async in Mind and reports back over the
  existing pipe, with a 30 s timeout (media 90 s) and cancellation when he closes the card.
- Hidden Sahar or unloaded Mind: no tool runs; MCP servers are stopped with the Mind and started again on first use.

## 5. Tool registry and classes

- `ToolSpec` gains `Source` (`Builtin` | `Mcp`), `ServerId`, `DescriptorHash` and `Sensitive`. MCP tools are announced
  as `mcp.<serverSlug>.<toolName>` (slug from his server name, `[a-z0-9_]`, unique), so two servers never collide.
- MCP `inputSchema` is converted to the existing `ArgSpec` subset (int, string, bool, enum, with min/max/maxLength).
  A tool whose schema does not fit is **not announced**; the page lists it as «هالأداة ما بتشتغل مع سحر بعد».
- Class is set by Sahar, never by the server's annotations:

| Class | Which tools | Default | "Always allow"? |
|---|---|---|---|
| Read | tools *he* marks «بس بتقرا» in the page | act | — (never asks) |
| B | every MCP tool by default; `image.make`, `voice.make` | ask | yes (D4), remembered per tool |
| B + Sensitive | names/descriptions matching delete/remove/send/post/pay/buy/transfer (Arabic and English list in Core), or marked by him | ask **every time** | no (D4) |
| C | nothing MCP can reach in 0.19 | refused | no |

- `ToolGrants` (settings, per tool): `ask` | `always` | `read`. Revocable in the page. `always` is ignored while the
  turn is *tainted* (§7).
- At most **12 MCP tools enabled at once** (page enforces): the small model's decision schema must stay short.

## 6. Adding a server (Settings → «الأدوات»)

- Two kinds only: **«رابط»** (Streamable HTTP: `https://…`, or `http://127.0.0.1`/`localhost`) and **«برنامج»** (a
  local `.exe` picked with the file dialog, optional arguments, working folder = its own folder).
- Optional secrets (API key/header or env values) are typed in the page and **sealed with DPAPI** like the 0.17 keys;
  given only to that server (HTTP header or that process's env), never logged, never shown again.
- On add: Sahar connects (`server/discover`, legacy fallback), lists tools, and shows each tool's name, its full
  description and its arguments **before** anything is enabled. He enables tools one by one.
- The `.exe` SHA-256 is recorded; if the file changes, the server is paused until he approves again.
- **Rug-pull guard:** each tool's `DescriptorHash` (SHA-256 of name, description, inputSchema, annotations) is stored
  when he enables it. On every `tools/list`, a changed or new tool goes to «بدها موافقة جديدة» and is not announced.
- No `sahar://` links, no "install from link", no OAuth (servers needing it show «مو مدعوم بعد»).
- A local ledger (`tools-ledger.json`) records when each server/tool was approved and its hash — no arguments, no output.

## 7. Safety of what tools return

- Every MCP output passes `ToolOutput.Sanitize` (Core, pure) before anything sees it: strip zero-width characters, the
  tag block U+E0000–U+E007F and bidi overrides (keep normal Arabic text and RLM/LRM), cap at 4 000 characters, drop
  non-text content except images (shown, never fed to the model).
- The sanitized text is shown to him in a **result card** labelled with the tool's name — it is the tool's words, not
  hers.
- If the turn needs a spoken answer, Mind runs **one more step with no tools allowed**: the output goes in as a
  `<tool_output source=… trust=untrusted>` block in the user turn, never in the system prompt.
- **Taint rule:** once untrusted output is in a turn, any further tool call in that turn asks him again, even if it is
  "always allowed". At most 3 tool calls per turn; the first error ends the turn.
- Tool output never enters her long-term memory unless he approves it (existing memory proposal flow).
- Her confirmation lines come from Core templates (as in 0.14), never from the tool's text.
- Logs and `perf.txt`: server index, tool name, class, verdict, duration, ok/error code. No arguments, outputs, prompts
  or file names.

## 8. Built-in media tools

**`image.make`** — «ارسميلي…»
- Mind writes a short English prompt from his words (decision JSON field `prompt_en`, max 300 chars), calls
  `https://image.pollinations.ai/prompt/<url-encoded prompt>` over HTTPS through the system proxy, saves the PNG to
  `Pictures\Sahar\` (`sahar-image-<yyyyMMdd-HHmmss>.png`), and shows it in the chat window with «افتح المجلد».
- Prompt text goes online by design (he asked for the picture); the ask card says so once: «رح ابعت وصف الصورة لخدمة
  Pollinations».
- 402 / `Retry-After`: she says how many seconds to wait; no silent retry, no queue.

**`voice.make`** — «اعمليلي ملف صوتي بيقول…»
- Groq `audio/speech` with `canopylabs/orpheus-arabic-saudi`, text ≤ 200 characters (longer: she says so and offers to
  shorten), saved as `Pictures\Sahar\sahar-voice-<…>.wav`, with a play button in the chat card.
- Uses the Groq key from 0.17; no key → the tool is not announced. Groq quota exhausted → she says so once (0.17 rule).

Both tools are hidden (not announced, no UI) until their provider check passes once.

## 9. Router

- Tool decisions always come from the **local** decision loop, so tool names, schemas and arguments do not leave the
  laptop just to *choose* a tool. 0.17's rule stays: online replies never run tools.
- When 0.18's big local model is installed, it handles the decision step for turns that involve MCP tools; native
  OpenAI `tools` stays off in 0.19 (behind an internal switch for testing only).
- The second, tool-less "read the output and answer" step follows the normal 0.17 route (online if allowed, else local),
  except when the tool is a local `.exe` server and «محلي فقط» is on.

## 10. Tests and verification

- Core xUnit: schema → ArgSpec conversion (fit / not fit), slug naming and collisions, `DescriptorHash` stability and
  change detection, `ToolOutput.Sanitize` (zero-width, tag block, bidi override, Arabic kept, cap), class + grant +
  taint decisions (including "always" ignored when tainted, sensitive never "always"), the sensitive-word list.
- Integration (Windows CI): a tiny test MCP server built in CI (stdio `.exe`) and a loopback HTTP test server: add,
  discover, list, enable, call, change a description → quarantined, kill on Mind exit, Job Object memory cap.
  Fake Pollinations and Groq endpoints on loopback: 402 handling, file saved, card shown.
- AOT: the Mind publishes with `ModelContextProtocol.Core` 2.4.0 and **zero new trim/AOT warnings** (Task 1 gate; if
  it fails, stop and report before building on it).
- UI: screenshots of the «الأدوات» page (light and dark), the ask card, the result card and the image/voice cards are
  reviewed and shown to him before publishing. Mind-eval gate stays ≥ 94 %.
- No real external API is called in CI.
